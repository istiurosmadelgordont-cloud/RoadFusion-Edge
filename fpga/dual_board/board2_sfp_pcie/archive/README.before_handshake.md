# HDMI → DDR → 图像增强 → PCIe 工程

此目录保存 2026-09-15 的 `hdmi_ddr_pice` 工程版本，用于 RoadFusion-Edge 的 FPGA 视频采集与 ARM 接收联调。

本次仅整理依赖、保存源码、补充说明；没有修复或改写现有 RTL，也没有实现新讨论的 RC 缓冲区所有权协议。此版本是开发基线，不是已经完成稳定性验证的发布版本。

## 2. 硬件与工具

- FPGA：PGL50H，Logos，FBG484，速度等级 -6（以工程配置为准）。
- 工具：Pango PDS 2022.2-SP6.4；需要兼容的工具安装和 IP 授权。
- HDMI 输入：RGB888、像素时钟、VS/HS/DE。
- DDR：32-bit 数据接口，用户侧数据总线为 256 bit。
- PCIe：当前顶层单 Lane 接口；实际协商速度/宽度要在 ARM 上确认。
- 默认视频：1920×1080；输出同步发生器使用 2200×1125 总时序。

IP 中的加密文件和厂商声明保持原样。纳入源码包不代表授予第三方 IP 的额外使用或再分发权限；使用者应遵守厂商授权。

## 3. 当前数据路径

HDMI RGB888 输入先截取为 RGB565，写入 DDR。DDR 在 `pix_clk_out` 域读出后还原为 RGB888，再送入亮度增强链，最后截取为 RGB565，通过异步 FIFO 和 PCIe MWr 写入 ARM DMA 内存。

注意：物理 HDMI 输出当前取自增强前的 `r_out/g_out/b_out`；增强后的数据只送入 PCIe。因此在 HDMI 屏幕上不一定能看到 ARM 设置的增强效果。

`pcie_dma_ctrl` 的 FIFO 写时钟已经使用 `pix_clk_out`，与此版本输入源一致。RGB565 拼接为 `{R[7:3], G[7:2], B[7:3]}`，共 16 bit。

## 4. 暗光与高光处理的实际含义

模块不是自动曝光/HDR，也没有直方图自适应功能。它先把 RGB 转为 YUV，在 Y 通道上执行阈值控制：

- 暗光提升开启且 `Y ≤ darkup_num`：增加 `(darkup_num - Y) >> 3`。
- 高光抑制开启且 `Y ≥ lightdown_num`：减少 `(Y - lightdown_num) >> 3`。
- U/V 基本保持不变，再转换回 RGB。

阈值范围是 0～255，不是直接加减的亮度值。两种开关可以同时开启，增减量按各自条件计算。RGB→YUV 的 3 级、YUV→RGB 的 4 级数据与同步流水线相互对应。

## 5. 当前 PCIe 视频协议

- 方向：FPGA EP 主动发起 Memory Write，写入 ARM RC 的 DMA 缓冲区。
- 地址：目前只支持 32-bit DMA 地址，采用 3DW MWr32。
- 单图像 TLP Payload：16 DW = 64 字节，不包含头部。
- 128-bit 用户接口：Header 单独一拍，随后四拍 Payload；最后一拍带 `TLAST`。
- 图像字节数：`1920 × 1080 × 2 = 4,147,200`，即 `0x3F4800`。
- 图像包数：64,800；随后一个 64 字节帧尾标记包。
- 每块 DMA 缓冲区至少：4,147,264 字节，即 `0x3F4840`，分配时可向页大小取整。
- 四块缓冲区：FPGA 在 VS 边界按索引循环选择，不按 ARM 的处理状态选择。

帧尾标记位于缓冲区偏移 `0x3F4800`，64 个字节都使用同一帧计数值。计数范围 1～255，完成帧后递增，255 后回到 1。它不是 32-bit 时间戳，也不是缓冲区归还确认。

未在下一 VS 前完成的旧帧会放弃剩余数据；已经向 PCIe IP 呈现的 TLP 则尽量完整发送后停止。这由 `abort_pending/stop_pending` 等逻辑处理。

## 6. ARM RC 操作要点

当前 BAR1 命令按 1 DW MWr 写入：

| BAR1 偏移 | 当前功能 |
| --- | --- |
| `0x110` | 依次登记四个 DMA 缓冲区的地址低 32 位 |
| `0x130` | 清除 DMA 地址配置并停止当前传输 |
| `0x140` | 设置高光抑制阈值并开启 |
| `0x150` | 设置暗光提升阈值并开启 |
| `0x160` | 关闭两种增强并清除阈值 |

当前视频控制器没有实现例程中的通用 `0x100` DMA 长度/类型命令或 `0x120` 地址高位命令，不要用旧例程寄存器表推断此版本功能。

驱动启动顺序：

1. 枚举设备、映射 BAR1，设置 32-bit DMA mask，启用 Bus Master。
2. 使用 Linux DMA API 分配四块缓冲区；提供 DMA/IOVA 地址，不提供用户虚拟地址。
3. 检查地址高 32 位为零、非零、容量足够，按既有协议使用至少 64 字节对齐的地址。
4. 清零缓冲区标记区，发送 `0x130` CLEAR，并按驱动规范确保控制写入可见。
5. 对 `0x110` 连续登记四个地址。第四个有效地址提交后，FPGA 等待完整 VS 边界开始采集。
6. 接收线程检查所有四块缓冲区的帧尾标记，记录新帧序号、时间和处理耗时；不能仅盲目假设下一块必定有新帧。

字节序必须沿用当前 DMA RTL 与 ARM 驱动的约定：地址命令使用 `endian32()`；增强阈值在 RTL 中取接收 DW 的 `[31:24]`。不要未经 AXIS/ILA 或寄存器实测就直接把阈值低字节写法当成已验证接口。

已有 ARM 详细联调说明见仓库 [`../pcie_video/`](../pcie_video/ARM端_PCIe彩条视频传输操作说明_修改版.md)。其中 DMA 格式和命令可供参考，但该文档不是本 DDR 工程的独立上板验证报告。

## 7. 四缓冲区限制与帧率

当前四缓冲区只是固定轮转，不存在 `FREE/WRITING/READY/READING` 所有权，也没有 ARM 归还寄存器。FPGA 不知道 CPU/NPU 是否仍在读取某块内存。

因此不能把此版本称为“保证读写不同页”的 RC 乒乓协议。尾标记不变、软件复制或增加缓冲区数量，都不能单独证明处理期间绝无覆盖；安全零拷贝需要额外的硬件/驱动交接机制。

下一版可增加空闲缓冲提交与归还握手：FPGA 只选择空闲块；完整帧通知 ARM；ARM 和异步 NPU/RGA 全部完成后才归还。实时模式无空闲块时跳过整帧，或只回收尚未被处理的旧 READY 帧，不能覆盖 READING 帧。该方案尚未在本快照实现。

提高帧率应先分别测量完整帧发送率、DMA 到达率和处理/显示率。1080p RGB565 的 60 fps 图像 Payload 约为 248.8 MB/s，还未计入 PCIe 协议开销。四缓冲只能缓解短时阻塞，不能解决处理平均速度不足。

后续优化方向（均非当前实现）：接收与推理分线程、减少整帧复制/颜色转换、合理共享 DMA 缓冲、双 Payload 暂存并行预取与发送，以及在协商 MPS 允许时增大 Payload。增大 TLP 必须限制到 `cfg_max_payload_size`、处理 4 KB 边界并更新包计数和帧尾协议。

## 8. 当前仍需处理的问题

1. `yuv2rgb.v` 使用 `result_*_18b[15:8]`，丢掉 `[17:16]` 后才判断 RGB 饱和。暗光提亮可使颜色回绕：RGB565 蓝色还原为 `(0,0,248)`，暗光阈值 255 时，按现有定点运算得到 `(28,28,20)`，正确限幅应为 `(28,28,255)`。应保留完整整数部分后限幅。
2. 增强阈值/开关由 `pclk_div2` 域更新，直接用于 `pix_clk_out` 域。运行中修改缺少多位原子交接与帧边界生效机制，可能出现瞬态阈值或同帧参数变化。
3. `axi_m.v` 的写页避让条件比较旧页，而且两个分支均写 `r_wr_addr_page + 1`，没有真正跳过正在读的下一页。DDR 页冲突仍需修正并用波形验证。
4. RC 四缓冲没有所有权反馈，存在循环覆盖正在处理帧的风险。
5. 增强模块的 `hs_in` 当前悬空；PCIe 不使用 HS，但后续接 HDMI/其他依赖行同步模块时应补齐。

先前发现的 FDC 末尾拼接损坏、A2/B3 重复分配，以及 PDS 未保存问题，在本次归档前的当前文件中已经更新：链路指示现在为 F7/F8，PDS 已登记新增模块。此处不把这些旧问题继续列为当前未修复项。
