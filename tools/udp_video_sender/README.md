# FPGA 视频 / 图片测试上位机

配套的 2026-09-16 FPGA 工程快照及固定接收参数见 [fpga/ethernet_video](../../fpga/ethernet_video/README.md)。

在 Windows 安装 Python 3 后双击 `start.cmd` 启动；首次运行会在本目录创建 `.venv` 并安装 `requirements.txt` 中的依赖，需要能访问 Python 包源。更新后请关闭旧窗口再打开。支持视频、静态图片和彩条。

## 输入与输出

- 输入分辨率：选择“原始尺寸”，或手动填写任意 `宽x高`，如 `800x600`。这是输入处理尺寸，不修改原文件。
- 输入采样 fps：可手动填写任意有限正数，例如 15、29.97、120。视频选择后自动带入原生帧率，随后可以修改。静态图片没有原生帧率，此项对静态内容无影响。
- 输出分辨率：实际写进网络帧头的宽高，像素数量也随之改变。没有固定 540p 画布。下拉框仅为常用预设，可以直接输入其他尺寸。
- 发送 fps：可填写任意有限正数，例如 0.5、25、59.94、120。它是目标帧率，实际帧率受带宽、解码和 Windows 定时精度限制，界面显示实际平均值。
- 等比留黑、居中裁剪、拉伸填满：分别应用于输入处理和输出尺寸转换。
- 图片取消循环时只发一帧；勾选后按发送帧率重复。视频支持播放至结尾或循环。

默认输出仍为 960×540 / 10 fps，与当前已验证的 FPGA 相容。其他输出尺寸用于后续修改过的 FPGA，必须同时调整其分辨率检查、像素计数和 DDR 帧缓冲。程序不再强制限制到 540p，也不会修改 FPGA。

输入/输出宽高范围为 1–65535（帧头每个字段 16 位），实际可处理尺寸受电脑内存和 OpenCV 限制；超大尺寸可能耗尽内存，并非承诺所有尺寸均能运行。帧率不编码在帧头里，由发送节奏控制。

## 帧率转换

例如原视频 30 fps、输入采样 30、输出 10：选取原帧 0、3、6…；输入采样 10、输出 30：每个采样帧重复发送三次。按视频时间线抽帧/重复帧，不对视频插值。性能不足时整体慢放，不突发补发来追赶时间。

参数在点击开始时固定，修改后需停止再开始。停止或关闭窗口会发完当前帧；不要强制终止进程。

## 网络配置

使用千兆直连网卡。本机例如 `192.168.1.102/24`，目标固定 `192.168.1.10:1234`，MAC 固定 `A0-B1-C2-D3-E4-E4`。当前 FPGA 无 ARP 应答，首次使用在本目录的管理员 PowerShell 执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\configure_network.ps1 -LocalIP 192.168.1.102
```

本机 IP 必须是连接 FPGA 的网卡实际地址。脚本只配置静态邻居映射，不修改网卡 IP。不要在接收期间向旧 FPGA 发送 ping 等其他协议报文。

## 线缆协议（供以后修改 FPGA）

每帧先发送独立的 8 字节 UDP 负载：

```text
F0 5A A5 0F  W高 W低 H高 H低
```

例如 1280×720 为 `F0 5A A5 0F 05 00 02 D0`。之后连续发送恰好 `W×H×2` 字节，从左到右、从上到下的大端 RGB565，每 UDP 负载最多 1200 字节，末包按实际剩余长度发送，不填充、不附加行头/序号/帧尾。红绿蓝分别为 `F8 00`、`07 E0`、`00 1F`。

**当 W×H 为奇数时，末包长度为 4n+2，接收端必须只输出最后一个有效像素，不能把 32 位字的残留低 16 位也当成像素。** 原接收器不支持这种末字处理；这属于未来 FPGA 需要支持的协议边界。没有为对齐而偷偷添加额外像素。

UDP 包数为 `1 + ceil(W×H×2 / 1200)`。960×540 仍为 1 个帧头包 + 864 个像素包。Windows/网卡生成 Ethernet、IPv4 和 UDP 头；启用禁止 IP 分片。

帧头后等待 2 ms，像素包逐包限速，帧末等待 2 ms。限速可设 1–950 Mbps，默认 120；这是软件速率上限，不代表 FPGA 吞吐保证。较高分辨率与帧率可能超过千兆链路或 DDR 能力，程序会降低实际速度，不承诺达到目标。纯像素带宽约为 `W×H×16×fps / 1000000` Mbps，还需计入协议及间隔开销。例如 960×540、120 Mbps 时仅发包就约需 75–80 ms，实际通常达不到 30 fps；1920×1080 在同样限速下发包约需 300 ms。界面会显示本帧的解码/转换时间和发包时间，便于判断瓶颈。

视频模式会在发送当前帧时准备下一帧，最多预取一帧，仍由单个发送线程按原顺序发完整帧。界面还显示“等待画面”时间：它较高表示解码/缩放跟不上；“发包”时间较高表示限速、网卡或逐包提交成为瓶颈。Windows 帧间等待采用精确截止时间，避免短 `Event.wait` 被系统时钟向上舍入。目标帧率不会自动提高链路速率；例如 960×540 若设 30 fps，120 Mbps 的发包时间本身已超过每帧 33.3 ms。

Windows 对极短的 `sleep` 常有明显舍入误差。发送器对每包不足数毫秒的间隔使用高精度等待，以免 120 Mbps 设置下单帧发送被拖成约半秒；这会提高发送线程的单核 CPU 占用。较长间隔仍使用休眠，且等待超时时不会突发补发。实际网卡驱动和 FPGA 仍需上板观察。

该协议没有确认、重传或序号，网络丢包后旧 FPGA 无法自动恢复。发送报错后程序停止，不自动补发；必要时复位接收端再开始。本地预览和计数不表示 FPGA 已确认收到。

